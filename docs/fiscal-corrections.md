# Correction of an existing receipt

The administrator opens an order and uses the correction panel beside its
fiscal receipt. The form copies the saved fiscal request, including the original
tax rates and payment allocation. Current catalogue and profile settings do not
rewrite that source.

One correction operation creates two FFD 1.2 correction receipts:

1. Return of income (`calculationSign: 2`) reproducing the incorrect sale.
2. Income (`calculationSign: 1`) containing the corrected data.

Neither step calls the bank or changes the original checkout/payment. Missing
receipts and correction of normal return receipts are outside this workflow.
The editor and confirmation explain this operation in Russian.

## Installation

- Apply migration `000025_fiscal_corrections.up.sql` with the normal migration
  command before starting the updated backend.
- Rebuild/deploy the backend and administrator frontend.
- The bundled `third_party/goterminalfa` is updated to upstream commit
  `5cd39e8a5a490ef933ae21711e768f87f1b624d6`, retaining Pronogti's existing
  `closeShiftIfOpen` extension. If the driver is deployed separately, use the
  included driver or a version exposing both that shift helper and
  `createCorrectionReceipt` for the configured `ffd1.2` device. Rebuilding only
  the Pronogti backend does not update an independently running driver service.
- Live corrections use the existing `fiscal.allow_live` switch and the original
  receipt's production environment and saved live configuration. Test receipts
  stay in demo mode. The correction worker starts with the administrator service.
- Optional `fiscal.correction_time_zone` is an IANA time zone such as
  `Asia/Yekaterinburg`. Omission uses the backend process's local zone, matching
  a driver on the same host. Set it explicitly when the backend and KKT use
  different local zones. The form's calendar date becomes UnixTime tag 1178 in
  that zone; the KKT supplies the new fiscal document's actual issue time.

## Administrator API

All endpoints require an administrator session. POST requests also require the
existing session nonce header and same-origin protection. Create and resume
require an `Idempotency-Key` header.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/admin/payment-orders/{id}/corrections` | Source receipt, eligibility and correction history |
| POST | `/admin/payment-orders/{id}/corrections/preview` | Validated reversal and replacement; no device calls |
| POST | `/admin/payment-orders/{id}/corrections` | Durably queued correction operation |
| GET | `/admin/payment-orders/{id}/corrections/{correction_id}` | Both documents, attempts and full driver results |
| POST | `/admin/payment-orders/{id}/corrections/{correction_id}/resume` | Retry a definitively failed step, retaining its audit history |
| GET | `/admin/fiscal-corrections` | Recent correction history |

The create/preview body contains `source_version`, `reason`, `basis`
(`voluntary` or `prescription`), `prescription_number` when applicable,
`calculation_date` (`YYYY-MM-DD`), and `receipt`. The receipt uses the driver's
camelCase JSON names. Correction date, prescription and predecessor-reference
attributes inside the driver payload are generated by the backend, not accepted
as independent browser overrides. The original fiscal sign is placed in tag
1192 for both documents. Source-version validation prevents submitting an editor
based on an already superseded receipt.

`schema/fiscal_correction.yaml` describes a read-only history model. Generated
HTTP routes, write operations and frontend scaffolding are disabled. The manual
workflow owns its routes, audit rules and editor; regeneration must not replace
it with editable table CRUD.

## Recovery and refunds

Every document attempt has its own stable driver request ID. Dispatch is marked
durably before contacting the driver. A worker recovering an interrupted
dispatch only looks up that ID. A lost finalization response remains unknown,
even if the driver successfully cancelled an open document afterward.

The replacement starts only after the reversal is confirmed. A failed replacement
can be resumed without repeating the reversal. Retry creates a new request ID
only after the previous attempt is definitively failed; previous attempts and
responses remain in history. Unknown outcomes must be reconciled, never retried
as fresh fiscal documents. A saved driver journal may continue to report an
unknown result; it is not evidence that no document was issued.

Corrections and refunds serialize on the order/payment. An unfinished correction
blocks new refunds and other corrections. A prior non-rejected bank refund blocks
automatic correction. Completed corrections supply the fiscal data for later
refunds. The bank's original paid amount remains authoritative: corrected totals
or payment splits incompatible with the existing automatic refund workflow are
reported explicitly instead of producing a misleading return receipt.

The driver opens a closed shift automatically. An expired open shift can still
be rejected by the KKT; close it through the existing shift controls before
resuming a definitively failed correction.
